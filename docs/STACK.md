# Выбранный стек Skyrim Extraction

Дата решения: 2026-10-05. Статус: **принято для разработки; игровая интеграция ещё не проверена**.
Основание: собственный PvPvE-режим для 2–4 игроков с постоянной экономикой и потерей имущества.

## Состав

| Слой | Выбор | Назначение |
|---|---|---|
| Игра | Skyrim Special Edition из Steam, runtime 1.6.1170, Windows 11 x64 | Одна целевая версия для первого стенда и релиза; совместимость всего комплекта подтверждается в G1 |
| Сеть и общий мир | SkyMP; начальный исходный снимок `2849e676fe008925384b26f34476e382a30bd877` | Синхронизация клиентов, акторов и мира; свой серверный игровой режим |
| Доступ к игре | SkyrimPlatform из согласованной сборки SkyMP | События и применение состояния в Skyrim; версии компонентов нельзя обновлять независимо |
| Наш серверный режим и клиентский адаптер | TypeScript, строгая проверка типов, сборка в JavaScript | Правила сессии, проверка намерений, преобразование идентификаторов и проекция состояния |
| Постоянное ядро | Отдельный процесс Node.js 24.x + TypeScript; текущий JS-прототип переносится постепенно | Схрон, экспедиции, предметы, сделки, прогресс, миграции и очередь применения |
| База | SQLite, локальный диск, WAL, один сервис записи | Один небольшой сервер владеет своей экономикой; периодические резервные копии |
| Интерфейс | React + TypeScript + CSS; статический bundle через esbuild в Chromium/CEF SkyrimPlatform | Схрон, экипировка, контракты, улучшения и итог экспедиции; без отдельного веб-сервиса UI |
| Контент | Собственный ESP, Creation Kit; данные лута/контрактов/баланса в JSON | Использование разрешённых объектов базовой игры, свои размещения и настройки |
| Нативные изменения | C++ / CMake только для отсутствующих перехватов SkyMP/SkyrimPlatform | Закрытие конкретных ограничений, обнаруженных в G1; большой форк не включён в базовую оценку |
| Серверная поставка | Linux x86-64, Docker Compose: SkyMP и постоянное ядро | Воспроизводимый запуск и отдельные runtime; данные игры предоставляет владелец сервера |
| Проверки | `node:test`, SQLite-тесты с отдельными процессами, GitHub Actions Windows/Linux; отдельный игровой стенд | Автоматическая проверка ядра и ручная/инструментированная проверка настоящих клиентов |

Это целевой состав, а не описание уже установленного окружения. Сейчас реализованы JS/SQLite-ядро 0.4, TypeScript HTTP/проекция, React UI, начальная прогрессия/торговля/контракты, контейнер ядра и экспериментальная библиотека SkyMP; сервер и unit target SkyMP скомпилированы в CI, игровая интеграция не подтверждена. Версии npm-пакетов закреплены package-lock.json; серверный образ — digest после воспроизводимой сборки. Для клиента нужны совместимые зависимости выбранной сборки, включая SKSE/Address Library, если их требует её манифест. Полный манифест формируется в P1, без установки случайного набора последних версий.

Сервер Windows не входит в обязательную поставку 1.0; проверка ядра на Windows не означает поддержку всего сервера. Локальная одиночная игра на Windows использует тот же Linux-сервер через WSL2/Docker; этот путь установки тоже входит в проверку P7. Внешний сервер позволяет клиенту обойтись без локального серверного окружения.

## Почему SkyMP

Нам нужны собственные правила владения предметами, смерти, возврата и прогресса. У SkyMP есть расширяемые свойства/события и SkyrimPlatform с TypeScript и Chromium. Это даёт конкретные точки для реализации режима и UI, доступные для изучения в исходниках. Выбор в пользу SkyMP — инженерный вывод из соответствия этих точек нашей архитектуре, а не доказательство готового PvPvE.

STR остаётся полезным ориентиром для кооперативной синхронизации. Его разработчики прямо указывают, что PvP не был основной целью; документация также описывает ограничения подбора выброшенных предметов и паузы. Для нашего режима выбираем SkyMP и сосредоточиваем эксперимент на нём. Параллельную реализацию для двух сетевых движков не ведём.

## Границы процессов и доверия

1. Клиентский адаптер отправляет намерения через сетевой канал SkyMP. UI не обращается непосредственно к постоянной базе.
2. Серверный адаптер SkyMP связывает сообщение с аутентифицированным персонажем и поколением подключения, проверяет состояние мира и допустимость действия.
3. Адаптер обращается к постоянному ядру по закрытому HTTP/JSON API с версией протокола и серверной аутентификацией. В Compose порт ядра не публикуется; секрет создаётся при установке, а не хранится в репозитории.
4. Ядро атомарно сохраняет экономический результат, квитанцию и задание на применение. Серверный адаптер применяет подтверждённую ревизию в игру и сверяет результат после переподключения.

SQLite является единственным источником постоянной экономики. Сохраняемые свойства SkyMP не становятся вторым независимым схроном. Позиции, бой и порядок событий принадлежат игровому серверу; экономическое ядро не пытается моделировать кадры Skyrim. При недоступности ядра операции с имуществом блокируются до восстановления и сверки.

На начальном снимке Dockerfile SkyMP использует Node.js 22, а наше ядро требует Node.js 24 с `node:sqlite`. Поэтому ядро работает отдельно, а не импортируется в runtime движка. Это также изолирует миграции и тестирование восстановления. Документация сборки местами расходится с актуальными build-файлами: версии компилятора, runtime и базового образа подтверждаем сборкой. Базовый образ для релиза должен поддерживаться на момент выпуска.

Серверный API не делает событие автоматически доверенным. Например, документация SkyMP показывает смерть, обнаруженную клиентским скриптом и переданную на сервер. Такое сообщение само по себе не разрешает потерю/выдачу имущества, награду за убийство или экстракцию. G1 должен подтвердить, что наш сервер умеет проверять эти исходы и пресекать влияние неподтверждённых предметов на бой; при нехватке API оцениваем нативный перехват.

## Обязательная проверка G1

Стек выбран сейчас. G1 проверяет пригодность выбранного стека, а не откладывает выбор до установки игры. На двух клиентах проверяем бой, NPC, общий предмет, смерть и чужой лут, интерьеры, отключение, старое сохранение и применение серверного отказа. Полный протокол находится в [плане](DEVELOPMENT_PLAN.md).

Фиксируем commit, версии клиента/сервера/Skyrim, модлист и результаты pass/fail с воспроизведением. Если ключевые проверки не проходят и требуют смены сетевой архитектуры, оформляем новое решение и пересчёт. Текущий бюджет включает ограниченные исправления интеграции, но не разработку нового мультиплеерного движка. PvP и критерии сохранности предметов сохраняются.
