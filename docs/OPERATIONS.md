# Постоянный сервис и восстановление

Это поставка только ядра экономики. Она не запускает Skyrim/SkyMP и не заменяет игровой сервер. Docker-проверка выполняется отдельной CI-задачей; локальная среда разработки Docker не предоставляет.

## Docker Compose

```sh
docker compose build
docker compose run --rm init
docker compose up -d --wait core
```

Инициализацию выполнять один раз: существующий ключ не заменяется. Ключ и SQLite находятся в named volume core-data, не в образе. Сервис работает пользователем node, с read-only root, без capabilities; порт опубликован только на 127.0.0.1. Для размещённого на другой машине адаптера требуется отдельный закрытый канал и TLS; публикация API напрямую в интернет не предусмотрена.

```sh
docker compose exec -T core node scripts/health.ts
docker compose exec -T core node scripts/doctor.mjs
docker compose exec -T core node scripts/backup.mjs data/core.sqlite data/backup-001.sqlite
```

Doctor читает согласованный снимок базы без изменений, проверяет схему, quick_check/FK, показывает ревизию/ack и суммарные счётчики без идентичностей и секретов. Health проверяет приватный HTTP с ключом внутри контейнера. Состояние healthy означает доступность ядра, не готовность Skyrim-клиентов.

Backup включает WAL и отказывается перезаписывать файл. Для защиты от потери диска копию нужно вынести с сервера в закрытое хранилище; named volume сам по себе не является резервной копией. Не публиковать игровые базы, ключи, профили и бэкапы в GitHub.

`docker compose down` останавливает сервис, сохраняя volume. **Не используйте down -v на рабочем сервере:** это удаляет постоянные данные. В CI эта команда очищает исключительно одноразовый тестовый volume.

## Восстановление

1. Заблокировать экономические взаимодействия в адаптере и остановить его вместе с ядром.
2. Сохранить аварийное состояние для расследования; проверить выбранную резервную копию отдельно.
3. Восстановить базу в остановленный сервис; не смешивать файл из копии с WAL/SHM от другой базы. Старые вспомогательные файлы предварительно переместить вместе с аварийной базой.
4. Запустить ядро, проверить doctor и содержимое собственного административного журнала.
5. Полностью сверить проекцию с игровым миром. Если ревизия откатилась или databaseId сменился, адаптер нельзя просто разблокировать: нужна явная повторная инициализация привязок и полного состояния.
6. Разрешить действия только после подтверждённой сверки обоих клиентов. Эта последняя стадия требует G1.

Смена ключа выполняется только при остановленных ядре/адаптере с обновлением ключа у доверенного адаптера. Не передавать его UI. Образ использует точный Node tag; digest и публикация образа фиксируются отдельно перед релизной поставкой.

## Проверка CI

Изолированный volume: init → healthy → регистрация тестового персонажа → restart → повтор с теми же квитанциями → backup → doctor. Игровых данных и пользовательских ключей в этой проверке нет. Результат компиляции SkyMP относится к отдельному workflow.
